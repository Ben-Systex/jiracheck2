# Feature Specification: 定時排程服務與服務執行紀錄

**Feature Branch**: `002-scheduled-services`
**Created**: 2026-05-22
**Status**: Draft
**Input**: User description: "定時啟動功能：可由使用者設定多組啟動服務的 ID、頻率與時間；執行均寫入 ServiceLogs（時間/服務ID/結果/說明/備註）。服務清單：CHKPROJ（依專案檢查清單檢查專案是否延遲）、CHKISSUE（檢查所有專案中有任務 / 無任務的清單與統計）。"

## 語彙

- **排程（Schedule / ScheduleConfig）**：觸發容器，有頻率、執行時間、啟用狀態與「下次預定時間」；不含執行邏輯。
- **服務（Service）**：被觸發執行的固定邏輯；v1 為 `CHKPROJ` / `CHKISSUE` 兩個內建服務，加上 `SYSTEM_CLEANUP`（系統內部紀錄保留）。
- **執行（Execution / ServiceLog）**：一筆排程 × 一次觸發 = 一筆 ServiceLog；含開始 / 結束時間、結果、說明、備註。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 設定多組定時服務並按時自動執行 (Priority: P1)

身為 Jira 小幫手的管理者或 PM，我希望能在「定時服務」設定頁建立多組排程：每一筆指定要執行的服務 ID（例如 CHKPROJ、CHKISSUE）、執行頻率（每日 / 每週 / 每月 / 自訂 cron 字串）以及實際的觸發時間，系統會在指定的時點自動啟動該服務並回寫結果。

**Why this priority**: 這是整個功能的「容器」，沒有它，CHKPROJ / CHKISSUE 就無法被自動觸發。它必須最先到位且可獨立驗證——只要能設定一筆排程、看到時點被觸發、結果寫入 ServiceLogs，整個 P1 就有完整的端到端閉環。

**Independent Test**: 即使 CHKPROJ / CHKISSUE 的內容只是「回傳一個固定字串」的假服務，只要使用者能新建排程、看到它被準時觸發、看到 ServiceLogs 收到一筆紀錄，即代表通過。

**Acceptance Scenarios**:

1. **Given** 使用者進入「定時服務」設定頁，**When** 新建一筆排程（服務 ID = CHKPROJ、頻率 = 每日、時間 = 09:00），**Then** 系統儲存該排程並顯示「下次執行時間」（例如「明天 09:00」）。
2. **Given** 使用者已建立一筆每日 09:00 的 CHKPROJ 排程，**When** 系統時間到達 09:00，**Then** 系統自動觸發 CHKPROJ 並於 ServiceLogs 寫入一筆紀錄（含執行時間、服務 ID、結果、說明、備註）。
3. **Given** 使用者同時設定 CHKPROJ（每日 09:00）與 CHKISSUE（每週一 09:30）兩筆排程，**When** 兩個時點分別到達，**Then** 兩筆都各自被獨立觸發，互不阻塞、各自於 ServiceLogs 寫入紀錄。
4. **Given** 使用者要停用某筆排程，**When** 在設定頁將該筆狀態切換為「停用」，**Then** 系統不再於指定時點觸發該排程，但保留歷史紀錄以利稽核。
5. **Given** 使用者要編輯排程的時間，**When** 將每日 09:00 改為每日 11:00 並儲存，**Then** 系統的「下次執行時間」即時更新為今天 11:00（或明天 11:00，視當下時間而定）。

### User Story 2 - 服務執行紀錄（ServiceLogs）檢視與查詢 (Priority: P2)

身為管理者或維運人員，我希望能進入「服務執行紀錄」頁，依時間 / 服務 ID / 執行結果（成功 / 失敗）查詢歷史紀錄，並可閱讀每筆的詳細「說明」與「備註」內容，以便進行問題排查與稽核。

**Why this priority**: 排程一旦上線，「我這次到底有沒有被執行」「為什麼上週六沒跑成功」這類問題會立即出現。沒有可查詢的紀錄頁，P1 等於沒有可見性。它依賴 P1（要先有紀錄寫入），所以排為 P2。

**Independent Test**: 給定 ServiceLogs 中已有 50 筆既有紀錄，使用者能依「最近 7 天 + CHKPROJ + 失敗」過濾，並看到正確子集與每筆的完整欄位即代表通過。

**Acceptance Scenarios**:

1. **Given** ServiceLogs 中已累積多筆紀錄，**When** 使用者進入「服務執行紀錄」頁，**Then** 系統預設顯示最近 7 天的紀錄，依執行時間遞減排序，並顯示每筆的：執行時間、服務 ID、執行結果、說明、備註。
2. **Given** 紀錄頁顯示了多筆資料，**When** 使用者套用過濾條件（服務 ID = CHKPROJ、結果 = 失敗、時間區間 = 上週），**Then** 系統僅列出符合條件的紀錄。
3. **Given** 使用者點擊任一紀錄的「詳細」按鈕，**When** 進入詳細頁，**Then** 系統顯示完整內容（包括長文字的「說明」與「備註」、相關專案清單、錯誤訊息原文等）。
4. **Given** ServiceLogs 資料量極大（例如累積一年），**When** 使用者翻頁或匯出，**Then** 系統能在合理時間內回應，且支援匯出（例如 CSV）以供離線分析。

### User Story 3 - 服務「CHKPROJ」：依專案檢查清單檢查專案是否延遲 (Priority: P2)

身為主管或 PM，我希望系統能在指定時點自動掃描「專案檢查清單」中所列出的每一個專案代號，判斷該專案目前是否有延遲狀況（例如：當前 Sprint 任務未完成且接近 Sprint 結束、Due Date 已過但仍未完成的任務數、整體 Story Points 預估與實際偏差過大等），並把結論寫入 ServiceLogs 供我事後檢視或寄送告警。

**Why this priority**: 與 P2「ServiceLogs 檢視」併行，因為兩者互為前後台。沒有 CHKPROJ 的實際邏輯，P1 的觸發機制等於只跑「空殼」。

**Independent Test**: 給定一份內容固定的「專案檢查清單」（如 PROJ-A、PROJ-B、PROJ-C），人為製造 PROJ-B 有 5 筆已逾期任務、PROJ-C 無延遲，手動觸發 CHKPROJ，ServiceLogs 中該筆紀錄能正確顯示「3 個專案、其中 1 個延遲」並列出延遲明細即代表通過。

**Acceptance Scenarios**:

1. **Given** 「專案檢查清單」內含 5 個專案代號，**When** 系統依排程或手動觸發 CHKPROJ，**Then** 系統逐一檢查每個專案的延遲狀況，於 ServiceLogs 中寫入一筆紀錄，「結果」標示為「成功」並於「說明」中總結（例如：5 個專案，2 個延遲、3 個正常）。
2. **Given** 「專案檢查清單」中某個專案代號於 Jira 已不存在或本服務無權限存取，**When** CHKPROJ 執行到該專案，**Then** 系統不中斷，將該專案的問題記在當筆紀錄的「備註」中，並把整體結果標為「部分失敗」。
3. **Given** 「專案檢查清單」為空，**When** CHKPROJ 被觸發，**Then** 系統不執行檢查，於 ServiceLogs 寫入一筆「結果 = 略過、說明 = 專案檢查清單為空」的紀錄。
4. **Given** CHKPROJ 偵測到延遲的專案，**When** 寫入 ServiceLogs，**Then** 該筆「說明」中需明列哪些專案延遲、各延遲多少筆任務、最嚴重的延遲天數，且使用者可點擊跳到該專案。

---

### User Story 4 - 服務「CHKISSUE」：統計有任務 / 無任務專案清單 (Priority: P3)

身為主管，我希望系統能定期統計「目前所有可見專案中，有任務的專案 vs. 完全沒有任務的專案」分別有哪些、各有幾個，並把結果寫入 ServiceLogs。沒有任務的專案往往代表休眠或棄置，定期掌握能協助管理。

**Why this priority**: 屬於「健檢類」資訊，可在 CHKPROJ 與 P2 完成後再上，能獨立驗證且不影響核心流程。

**Independent Test**: 給定一個 Jira 環境中有 10 個可見專案、其中 3 個完全沒有 issue、7 個至少有 1 個 issue，手動觸發 CHKISSUE，ServiceLogs 中該筆紀錄能正確顯示「總數 10、有任務 7、無任務 3」並列出兩組清單即代表通過。

**Acceptance Scenarios**:

1. **Given** 系統可見 N 個 Jira 專案，**When** CHKISSUE 被觸發，**Then** 系統於 ServiceLogs 寫入一筆紀錄，「說明」中包含：總專案數、有任務的專案數、無任務的專案數，並以可讀形式列出兩組清單。
2. **Given** 系統當下完全沒有可見專案，**When** CHKISSUE 被觸發，**Then** 寫入「結果 = 略過、說明 = 目前無可見專案」的紀錄。
3. **Given** 某個專案在執行過程中暫時 API 失敗，**When** CHKISSUE 執行，**Then** 系統不中斷，記錄該專案「狀態未知」於備註中並把整體結果標為「部分失敗」。
4. **Given** CHKISSUE 連續多次（例如 4 週）皆指出同一個專案無任務，**When** 寫入 ServiceLogs，**Then** 系統在「備註」中標註「已連續 N 次無任務」，協助管理者判斷是否歸檔。

---

### Edge Cases

- 系統重啟、部署或暫時停機，導致某筆排程的觸發時點被錯過：應有明確策略（是否補跑、是否略過並寫入「錯過」紀錄）。
- 上一次同服務 ID 還在執行中，但下一次排程時點又到了：應避免重複併發執行（同 ID 視為互斥）。
- 使用者在排程編輯頁輸入不合法的時間（如「2 月 30 日」「25 點」）：必須在儲存時阻擋並提示錯誤。
- 自訂 cron 字串解析失敗：必須在儲存階段阻擋，不允許不合法字串入庫。
- 時區變更：使用者個人時區與伺服器時區若不一致，應以哪一個為準需明確（建議伺服器時區，並在 UI 標示）。
- ServiceLogs 累積一段時間後資料量過大：應有保留策略（例如保留 1 年、或分層儲存歷史），避免效能下降。
- 多位管理者同時編輯同一筆排程造成版本衝突：應採「最後寫入者勝出 + 顯示警示」或「樂觀鎖」策略，避免靜默覆寫。
- CHKPROJ 的「專案檢查清單」資料來源於何處（系統內部表 / Confluence 頁面 / 外部檔案）需明確；本 spec v1 假設為系統內部維護。
- 服務執行因外部依賴（Jira API 暫時失敗）而失敗時，應提供有限次數的自動重試，且每次重試結果都要可追溯。

## Requirements *(mandatory)*

### Functional Requirements

#### 排程設定與觸發（US1）

- **FR-001**: 系統 MUST 提供「定時服務」設定頁，讓使用者新增、編輯、停用、啟用、刪除排程設定。
- **FR-002**: 每筆排程設定 MUST 至少包含：服務 ID、執行頻率（每日 / 每週 / 每月 / 自訂 cron）、執行時間、啟用狀態、建立者、**最後更新者**、最後更新時間。
- **FR-003**: 系統 MUST 在儲存排程前驗證時間 / 頻率的合法性，禁止不合法字串入庫。
- **FR-004**: 系統 MUST 對每筆啟用中的排程顯示「下次預定執行時間」，並在編輯後即時更新。
- **FR-005**: 系統 MUST 在排程時點到達時自動觸發對應的服務 ID，並將該次執行記錄於 ServiceLogs。
- **FR-006**: 系統 MUST 確保同一服務 ID 不會同時併發執行；若上一次尚未完成而下一次時點已到，第二次應被略過並寫入「略過」紀錄。
- **FR-007**: 使用者 MUST 能對任何排程「手動立即執行一次」，並產生與自動觸發相同格式的 ServiceLogs 紀錄。**手動執行同樣受 FR-006 互斥約束；若同服務 ID 仍在執行中，第二次點擊一律寫入 `result = skipped` 紀錄並回應 202 + 該 skipped 紀錄 id（前端應以 toast 揭示「上一次仍在執行，本次略過」）**。
- **FR-008**: 系統 MUST 對排程的觸發採用伺服器時區為唯一基準，並在 UI 明確顯示時區字樣，避免使用者誤解。

#### ServiceLogs 紀錄與查詢（US2）

- **FR-010**: 系統 MUST 為每次服務執行寫入一筆 ServiceLogs，欄位至少包含：執行時間（開始 / 結束）、服務 ID、執行結果（成功 / 部分失敗 / 失敗 / 略過）、說明、備註、觸發來源（排程 / 手動）。
- **FR-011**: 系統 MUST 在「服務執行紀錄」頁預設顯示最近 7 天紀錄，並支援依服務 ID、結果、時間區間進行過濾。
- **FR-012**: 系統 MUST 為每筆紀錄提供「詳細」檢視，顯示完整「說明」與「備註」（不被列表截斷）。
- **FR-013**: 系統 MUST 提供匯出功能（至少 CSV 格式），可將目前過濾後的結果匯出。
- **FR-014**: 系統 MUST 將 ServiceLogs 保留 90 天，超過 90 天的紀錄由系統自動刪除；刪除動作本身亦需在系統內部留下可稽核的執行紀錄（例如維運排程的日誌）。
- **FR-015**: 系統 MUST 限制 ServiceLogs 的讀取權限為管理者 / PM 角色，一般使用者不可見。

#### 服務 CHKPROJ（US3）

- **FR-020**: 系統 MUST 在被觸發時讀取「專案檢查清單」（系統內部維護的清單），逐一檢查每個專案代號。
- **FR-021**: 系統 MUST 採用以下固定規則判斷專案「延遲」（v1 寫死於系統，v1.1 再考慮做成可配置），並把使用的規則版本與判斷依據明確記錄於該次 ServiceLogs 的「說明」欄位中：
  - 條件 A：當前進行中的 Sprint 已過半（時間軸），且 Story Points 完成率 < 50%；或
  - 條件 B：該專案中存在任一未完成（非 Done）任務，其 Due Date 已逾期 ≥ 3 天。
  - 符合 A 或 B 任一者即判定為「延遲」。每筆紀錄需明列觸發的條件（A / B / 兩者），以及實際數據（如：Sprint 進度 65%、完成率 32%、逾期任務 5 筆 / 最長 11 天）。
- **FR-022**: 系統 MUST 當某專案不存在或無權限存取時，僅將該專案的問題記在備註，不可使整批執行失敗。
- **FR-023**: 系統 MUST 在「專案檢查清單」為空時，仍寫入一筆 ServiceLogs（結果 = 略過、說明清楚標示），避免使用者誤以為服務未執行。
- **FR-024**: 系統 MUST 在 ServiceLogs 紀錄中讓使用者可一鍵跳到延遲專案的詳細頁（連結到專案儀表板）。
- **FR-025**: 系統 MUST 提供「專案檢查清單」的維護介面，讓管理者新增 / 移除被檢查的專案代號。

#### 服務 CHKISSUE（US4）

- **FR-030**: 系統 MUST 在被觸發時，列出所有目前可見的 Jira 專案，並逐一判斷是否「有任務」（issue 數 > 0）或「無任務」（issue 數 = 0）。
- **FR-031**: 系統 MUST 於 ServiceLogs 寫入「總專案數、有任務專案數、無任務專案數、兩組清單」。
- **FR-032**: 系統 MUST 在連續多次（門檻可設定）皆判定為「無任務」時，於該筆紀錄的備註中標示警示（例如「連續 N 次無任務」），協助管理者判斷是否歸檔。
- **FR-033**: 系統 MUST 對單一專案 API 暫時失敗的情況採部分失敗處理，不可使整批執行中斷。

### Key Entities *(include if feature involves data)*

- **ScheduleConfig（排程設定）**: 紀錄一筆排程的服務 ID、頻率（每日 / 每週 / 每月 / 自訂）、執行時間、啟用狀態、下次預定時間、建立 / 更新者、時區。
- **ServiceLog（服務執行紀錄）**: 一次執行的完整紀錄，至少包含開始時間、結束時間、服務 ID、觸發來源（排程 / 手動）、結果、說明、備註、執行人 / 系統識別。
- **ProjectCheckList（專案檢查清單）**: CHKPROJ 服務的輸入來源，內含使用者欲檢查的專案代號清單與最後更新時間 / 更新者。
- **DelayJudgmentRule（延遲判斷規則）**: 用於 CHKPROJ 對「延遲」的明確判斷準則描述。v1 為固定版本「rule-v1」：規則 A（Sprint 過半且 Story Points 完成率 < 50%）或規則 B（任一未完成任務 Due Date 逾期 ≥ 3 天）。寫入 ServiceLogs 時需附上規則版本號，便於稽核時還原當時的判斷邏輯。
- **ProjectIssueSnapshot（CHKISSUE 結果快照）**: 每次 CHKISSUE 執行所得的「有任務 / 無任務」清單快照，可用於連續性分析（例如連續 N 次無任務的提醒）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 對於設定的排程，95% 以上的執行需準時觸發（與設定時間誤差不超過 1 分鐘）。
- **SC-002**: 每一次服務執行（含成功 / 失敗 / 略過）100% 都會在 ServiceLogs 中留下對應紀錄；「不見的紀錄」被視為嚴重缺陷。
- **SC-003**: 使用者於「服務執行紀錄」頁套用任一過濾條件，結果應於 2 秒內顯示，且過濾條件無誤。
- **SC-004**: CHKPROJ 對 50 個專案的清單，於 Jira API 正常時應於 5 分鐘內完成檢查；對於部分專案失敗的情況，整體執行仍能完成並寫入紀錄。
- **SC-005**: CHKISSUE 對 200 個專案的環境，於 Jira API 正常時應於 10 分鐘內完成檢查並寫入結果。
- **SC-006**: 上線後第二個月起，管理者每週至少查閱一次 ServiceLogs，且「漏掉延遲專案直到 PM 自行回報」的案例數降為 0。
- **SC-007**: 對於明顯異常的執行結果（例如連續 3 次失敗），系統的可發現性使管理者能在當週內介入；不必等使用者自行回報。

## Assumptions

- 本功能屬於 Jira 小幫手（spec 001-jira-assistant）系統的子模組，沿用其使用者身份與 session middleware。**管理者角色判定於 v1 採 `ADMIN_ACCOUNT_IDS` 環境變數白名單（research [R-002](./research.md#r-002管理者角色判定fr-015)）**；v1.1+ 才考慮升級為 `users.role` 表級角色管理。
- 「專案檢查清單」屬於本系統內部維護的資料，不從 Confluence、外部檔案或第三方系統匯入；管理者透過本工具的設定頁維護。
- 排程觸發時點以伺服器時區為唯一基準，UI 會顯示「Asia/Taipei」等明確字樣；使用者個人時區的呈現不在 v1 範圍。
- ServiceLogs 中的「說明」欄位以人類可讀的中文為主，主要對象是管理者與 PM；機器解析格式（如 JSON 細節）可放在「備註」或詳細頁。
- v1 不提供任何對外通知（Email / Slack / Webhook）；異常一律由管理者主動進入「服務執行紀錄」頁查看。Email / Slack 整合列為下版本（v1.1+）的擴充項，與本 spec 範圍切割。
- CHKPROJ 的「延遲」規則於 v1 採固定規則「rule-v1」（A 或 B 任一觸發）寫死於系統，v1.1 再考慮做成可配置。
- 排程設定的修改一律走「最後寫入者勝出 + 顯示警示」策略，並在編輯頁顯示最後更新者與時間，協助雙人協作。
- 服務在外部依賴失敗時可自動重試 1–2 次（短間隔），每次重試均寫入紀錄；超過重試次數則視為失敗，由管理者人工介入。
- CHKPROJ 與 CHKISSUE 為內建固定服務集合，v1 不開放使用者自行擴充新服務 ID；新增服務需以版本更新方式發布。
