# Feature Specification: Jira 小幫手

**Feature Branch**: `001-jira-assistant`
**Created**: 2026-05-22
**Status**: Draft
**Input**: User description: "Jira 小幫手 — 使用自然語言查詢專案資訊、任務、人員工作項目與完成狀態；提供專案儀表板、人員工作狀況統計與 issue 整批更新功能。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 專案儀表板與快速搜尋 (Priority: P1)

身為一位 Jira 使用者（例如 PM、開發人員、測試人員、主管），當我打開「Jira 小幫手」時，我希望能立即看到自己最近關注的專案概況，並能透過關鍵字快速找到想看的專案，不必再進到 Jira 後台翻找。

**Why this priority**: 這是進入產品的第一個畫面，也是所有其他功能（查任務、查人員、批次更新）會回到的「導覽中心」。沒有它，使用者就無法以「以專案為視角」的方式啟動其他操作；具備這項功能本身就能立即提供「省去進 Jira 找專案」的價值，可作為獨立 MVP 上線。

**Independent Test**: 在尚未實作其他功能（自然語言查詢、人員統計、批次更新）的情況下，使用者只要能登入工具，看見自己最近存取的 5 個專案儀表板、輸入專案關鍵字並看見符合結果即代表通過。

**Acceptance Scenarios**:

1. **Given** 使用者已連線到自己的 Jira 帳號且過去曾存取過至少 5 個專案，**When** 使用者開啟工具首頁，**Then** 系統顯示最近存取紀錄的前 5 個專案儀表板卡片，每張卡片至少顯示專案名稱、Key、未完成任務數、本期 Story Points 完成比例。
2. **Given** 使用者過去存取的專案少於 5 個（或為新使用者），**When** 使用者開啟工具首頁，**Then** 系統顯示所有已存取的專案，並提示「使用上方搜尋框尋找更多專案」。
3. **Given** 使用者在搜尋框輸入「pay」這類關鍵字，**When** 按下搜尋或停止輸入 500ms 後，**Then** 系統列出名稱或 Key 中包含「pay」的所有可存取專案，並可一鍵切換為儀表板檢視。
4. **Given** 使用者點擊任一專案卡片，**When** 進入該專案儀表板，**Then** 該專案即被記錄為「最近存取」，下次首頁將反映新的排序。

---

### User Story 2 - 自然語言查詢專案 / 任務 / 人員資料 (Priority: P2)

身為一位不熟悉 JQL 的使用者，我希望能用平常講話的方式（例如「給我看上週小明完成的任務」、「PayBox 專案還有幾個未完成 Bug？」）查詢 Jira 資料，並可以做簡單的統計（總數、加總、平均、分組）。

**Why this priority**: 這是本產品最具差異化價值的核心特色，也是使用者描述中明確指定的關鍵能力。但它依賴 P1（先有專案範圍），且實作複雜度較高（需要 LLM 解譯與安全約束），因此排為 P2。

**Independent Test**: 給定一個固定的測試 Jira 資料集，使用者輸入 10 個常見問句（混合「列出」「統計」「跨專案」三類），系統能夠：(a) 解讀後回傳正確的結果或統計；(b) 對於無法解讀的問句明確說明原因並提供建議改寫方式，即代表通過。

**Acceptance Scenarios**:

1. **Given** 使用者輸入「列出 PayBox 專案上週狀態為 Done 的所有任務」，**When** 送出查詢，**Then** 系統列出符合條件的任務（顯示 Key、標題、負責人、完成時間），並在結果區提供「我是這樣理解你的問題的」說明（例如顯示等效的篩選條件）。
2. **Given** 使用者輸入「小明這個月完成了幾個任務？總共 Story Points 是多少？」，**When** 送出查詢，**Then** 系統回傳一個含「任務數量」與「Story Points 加總」的統計結果，並列出明細以供驗證。
3. **Given** 使用者輸入語意不明的問句（例如「告訴我一些事」），**When** 送出查詢，**Then** 系統不會擅自執行查詢，而是請使用者補充：要查哪個專案 / 哪段時間 / 哪類資料。
4. **Given** 使用者要求的資料超出他在 Jira 中的可見範圍，**When** 送出查詢，**Then** 系統僅回傳該使用者有權限存取的部分，並明確標示「部分結果因權限限制未顯示」。

### User Story 3 - 人員工作狀況查詢與工時統計 (Priority: P3)

身為主管或 PM，我希望能挑選某位團隊成員，看見他在所有專案中的任務清單，並且能挑一段時間（例如本週、上個 Sprint、4/1–4/30）統計他的計畫工時（Story Points）與實際工時（Actual Story Points），以便進行人力盤點與績效對話。

**Why this priority**: 是管理層級的高價值功能，但相較於 P1/P2，受眾較窄（主管 / PM），且邏輯上可在儀表板與自然語言查詢就緒後再交付。它也可建立在 P2 的查詢能力之上。

**Independent Test**: 即便自然語言查詢未實作，使用者也能透過下拉選單選擇人員 + 時間區間，看到正確的跨專案任務清單與 Story Points 統計即代表通過。

**Acceptance Scenarios**:

1. **Given** 使用者在「人員工作狀況」頁面選擇成員「小明」，**When** 頁面載入，**Then** 系統列出小明在所有「使用者可存取之專案」中、目前狀態為「進行中或未完成」的所有任務，依到期日由近到遠排序。
2. **Given** 使用者選擇成員「小明」並指定時間區間 2026-04-01 至 2026-04-30（範例），**When** 送出查詢，**Then** 系統顯示該期間內小明完成任務的：(a) 任務數量、(b) Story Points 加總、(c) Actual Story Points 加總、(d) 估準度（Story Points / Actual Story Points 比值），並可展開明細。
3. **Given** 該員工任務跨多個專案，**When** 顯示清單，**Then** 每個任務需明確標示所屬專案名稱，並可一鍵跳到該專案儀表板（沿用 P1）。
4. **Given** 使用者選的人員在所選時間區間內沒有工作紀錄，**When** 送出查詢，**Then** 系統顯示「此期間無工作紀錄」並提供調整區間的建議按鈕（例如「擴大到三個月」）。

### User Story 4 - 整批更新 issue（含預覽確認） (Priority: P4)

身為 PM 或 Jira 管理員，我希望能挑選一個專案、設定篩選條件（例如「Sprint = Sprint 24 且 Status = To Do」）、設定要更新的欄位（例如把 Assignee 改成小華、把 Due Date 改成 5/30），然後在系統顯示的預覽清單中確認影響範圍後，再一鍵套用。

**Why this priority**: 屬於寫入型操作，影響範圍大、風險高，因此必須等前面的「可見性」功能（儀表板、查詢、人員清單）成熟、使用者已熟悉本工具後再上線；同時實作上需要更完整的權限保護與審計紀錄。

**Independent Test**: 即便沒有自然語言查詢，使用者也能透過表單方式（專案 → 篩選條件 → 變更欄位）完成從篩選到預覽到套用的完整流程，並可在 Jira 後台驗證實際變更與紀錄一致即代表通過。

**Acceptance Scenarios**:

1. **Given** 使用者選擇「PayBox」專案並設定篩選條件「Sprint = Sprint 24 且 Status = To Do」，**When** 點擊「預覽」，**Then** 系統列出所有符合條件的 issue（含 Key、標題、目前負責人），並顯示影響筆數。
2. **Given** 預覽列表顯示 35 筆 issue，使用者設定變更「Assignee → 小華」，**When** 點擊「套用」並於確認對話框輸入「確認更新 35 筆」，**Then** 系統執行更新，並回報每筆成功 / 失敗，最終顯示成功 34 筆、失敗 1 筆（含失敗原因）。
3. **Given** 使用者要更新的欄位他在 Jira 沒有編輯權限，**When** 嘗試送出更新，**Then** 系統在預覽階段就攔截並提示「您對下列 X 筆 issue 沒有編輯權限，請調整選取範圍」。
4. **Given** 使用者於確認對話框輸入錯誤的確認字串或按下取消，**When** 按下確認，**Then** 系統不進行任何寫入，並保留預覽結果以便繼續編輯條件。
5. **Given** 批次更新已執行完成，**When** 使用者重新整理頁面或返回首頁，**Then** 系統保留本次操作的歷史紀錄（誰、何時、影響哪些 issue、變更內容），以便日後查核。

---

### Edge Cases

- 當 Jira 暫時無法連線或回傳超時，工具應顯示明確錯誤並提供「重試」按鈕，而非顯示空白頁。
- 當使用者沒有任何可存取的專案時，首頁應顯示「您目前沒有可存取的 Jira 專案，請聯絡管理員」訊息。
- 當「最近存取紀錄」尚未建立（首次使用），首頁應呈現「請使用搜尋找到您要的專案」的引導，而非空白。
- 自然語言查詢結果筆數超過合理上限（例如 1000 筆）時，應提示「結果筆數過多，請加上更精確的條件（例如時間 / 專案）」，並只回傳前 N 筆。
- 整批更新的篩選條件回傳 0 筆 issue 時，應禁用「套用」按鈕並顯示「無符合條件的 issue」。
- 對於同一 issue，整批更新進行期間若另有他人也修改了該 issue，應以「Jira 版本衝突」處理並回報為部分失敗。
- 對於名字相同的成員或姓名變更後的同人，系統需以 Jira 帳號為唯一識別，避免統計合併錯誤。
- 整批更新的單次操作上限應有明確限制，超過時應提示分批執行。
- 使用者於不同時區操作（例如海外同仁），統計區間的「日」應有明確時區基準（預設使用者所在時區）。

## Requirements *(mandatory)*

### Functional Requirements

#### 通用 / 認證

- **FR-001**: 系統 MUST 讓使用者以自己的 Jira 帳號連線，並僅能存取該帳號於 Jira 中本有權限的資料（讀寫權限均以 Jira 為準）。
- **FR-002**: 系統 MUST 為每位使用者維護「最近存取專案」紀錄，依存取時間遞減排序。
- **FR-003**: 系統 MUST 於所有顯示 Jira 資料的畫面標明資料更新時間，並允許使用者手動「重新整理」。

#### 專案儀表板（US1）

- **FR-010**: 系統 MUST 在首頁預設顯示使用者最近存取的 5 個專案儀表板。
- **FR-011**: 系統 MUST 提供以「專案名稱 / Key 關鍵字」進行模糊搜尋並回傳使用者可存取的專案列表。
- **FR-012**: 每張專案儀表板卡片 MUST 至少呈現：專案名稱、Key、未完成任務數、本期（或進行中 Sprint）任務數、Story Points 完成比例。
- **FR-013**: 使用者 MUST 能從儀表板卡片點擊進入該專案的詳細頁，並將該動作記為一次「存取」。

#### 自然語言查詢（US2）

- **FR-020**: 系統 MUST 接受使用者以自然語言（中文 / 英文皆可）輸入查詢，並回傳結果。
- **FR-021**: 系統 MUST 在回傳結果同時，呈現「系統如何解讀您的問題」的可讀說明（例如：時間範圍、專案範圍、條件、統計方式）。
- **FR-022**: 系統 MUST 支援基本統計：計數、加總、平均、分組計數、Top-N 排序。
- **FR-023**: 系統 MUST 在無法解讀問句時，提示使用者補充必要資訊，而不擅自執行任意查詢。
- **FR-024**: 系統 MUST 嚴格僅查詢使用者於 Jira 有權限存取的資料，並對因權限被過濾的部分明確標示。
- **FR-025**: 自然語言查詢 MUST 為唯讀；不得透過自然語言介面執行任何寫入動作（寫入一律走 US4 的明確流程）。

#### 人員工作狀況（US3）

- **FR-030**: 系統 MUST 提供「選擇人員」的功能，可依使用者輸入關鍵字搜尋人員。
- **FR-031**: 系統 MUST 列出該人員在所有「使用者可存取之專案」中的任務，並標明所屬專案。
- **FR-032**: 系統 MUST 支援指定一段時間區間，並依此區間統計：完成任務數、Story Points 加總、Actual Story Points 加總、以及兩者之差異 / 比值。
- **FR-033**: 系統 MUST 以 Jira 帳號（accountId）作為人員的唯一識別，避免同名混淆。
- **FR-034**: 系統 MUST 在統計結果中提供「明細展開」功能，列出每一筆統計來源任務以便驗證。

#### 整批更新 issue（US4）

- **FR-040**: 系統 MUST 要求使用者先選擇單一專案，再設定篩選條件（至少支援：Status、Assignee、Sprint、Issue Type、Label、Due Date 區間等常見欄位的組合）。
- **FR-041**: 系統 MUST 在執行更新前提供「預覽」步驟，列出將被更新的 issue 與當前值。
- **FR-042**: 系統 MUST 在預覽階段檢查使用者對所列 issue 的編輯權限，並在使用者沒有權限的 issue 上明確標示。
- **FR-043**: 系統 MUST 在送出實際更新前要求使用者進行「明確確認」（例如輸入受影響筆數）。
- **FR-044**: 系統 MUST 對每筆更新回報成功或失敗及原因，並提供下載成功 / 失敗結果的能力。
- **FR-045**: 系統 MUST 對每次批次更新留下審計紀錄（誰、何時、條件、影響範圍、結果），並可供事後查詢。
- **FR-046**: 系統 MUST 對單次批次更新的最大筆數設限為 200 筆；超過 200 筆時需阻擋送出並提示使用者「請分批執行（每批最多 200 筆）」，同時在預覽階段即顯示剩餘可送出筆數。
- **FR-047**: 系統 MUST 將 v1 可批次更新的欄位限制於下列固定白名單：Assignee、Due Date、Label、Priority、Sprint。白名單以外的欄位（特別是 Status / 工作流轉換、自訂腳本欄位、計算欄位）一律於 UI 不顯示為可選項；新增欄位需以版本更新方式擴充，不開放使用者自行設定。

### Key Entities *(include if feature involves data)*

- **Project（專案）**: 對應 Jira 專案，至少包含 Key、Name、URL、最近存取時間、未完成任務數、目前 Sprint 等指標。
- **Issue（任務）**: 對應 Jira issue，至少包含 Key、Title、Status、Assignee（accountId）、Story Points、Actual Story Points、Sprint、Due Date、所屬 Project。
- **User（人員）**: 對應 Jira 帳號，包含 accountId、顯示名稱、Email、頭像 URL。
- **QueryHistory（查詢紀錄）**: 紀錄每次自然語言查詢的問句、解讀結果、結果摘要、執行時間，便於使用者回溯與系統改善。
- **BulkUpdateOperation（批次更新操作）**: 紀錄每一次批次更新的條件、預覽清單、變更欄位、確認人、執行時間、每筆結果與最終摘要。
- **RecentAccessLog（最近存取紀錄）**: 紀錄每位使用者對每個專案的最近存取時間，用以驅動首頁的「最近 5 個」排序。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 首頁能在使用者進入後 2 秒內顯示「最近 5 個專案」儀表板（含關鍵指標），且 95% 的查詢回應時間在 3 秒以內。
- **SC-002**: 對於 20 道事先準備的常見自然語言問句測試集，系統能正確解讀並回傳正確結果的比例達到 90% 以上；無法解讀的問句則 100% 給出「補充提示」而非錯誤資料。
- **SC-003**: 使用者完成「查某人某月工作量」的任務時間，由目前手動翻 Jira 的平均 5 分鐘以上，縮短到 30 秒以內。
- **SC-004**: 批次更新從進入功能到實際送出，至少需經過 1 次預覽 + 1 次明確確認，因此「誤更新」事件（事後需 rollback）次數應在上線後一季內維持為 0。
- **SC-005**: 每月批次更新功能處理的 issue 累計筆數，相較於使用者手動逐筆更新前，節省至少 70% 的人工時數（以使用者自陳估算為主，並輔以系統紀錄）。
- **SC-006**: 上線後第二個月起，每月活躍使用者中有 60% 以上會至少使用一次「自然語言查詢」功能。
- **SC-007**: 工具上 100% 的查詢結果只呈現使用者於 Jira 有權限的資料，並通過至少一次跨權限帳號的人工抽測。

## Assumptions

- 使用者每人均擁有自己的 Jira 帳號並能以該帳號完成認證，工具不使用共用服務帳號代為查詢，以確保權限隔離。認證方式統一採用 Atlassian OAuth 2.0（3LO 授權碼流程）：首次使用時導向 Atlassian 完成授權後，由系統保管 refresh token 自動延續；不採用個人 API Token 或公司 SSO 直連 Jira。
- Jira 中已存在「Story Points」與「Actual Story Points」兩個欄位（不論為原生或自訂），並由團隊既有流程填寫；工具不負責欄位建置。
- 本工具初期假設使用 Jira Cloud 環境，Jira Server / Data Center 的相容性不列入 v1 範圍。
- 自然語言處理採用第三方 LLM 服務即可，不需在本地端訓練模型；但所有送往 LLM 的內容必須不包含可識別個資以外的敏感欄位（細節由 plan 階段決定）。
- 介面語言預設為繁體中文，並能依使用者瀏覽器語系切換至英文。
- 預設時區為使用者瀏覽器或 Jira profile 中設定的時區，所有「日 / 週 / 月」統計皆以此為準。
- 「最近存取的 5 個專案」以本工具的存取紀錄為準（非 Jira 內建紀錄），可由本工具自行維護。
- 批次更新限定於 v1 不開放「跨專案」操作，必須單一專案逐個進行，以降低風險。
